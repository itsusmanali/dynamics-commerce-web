# Dynamics modules — beginner guide

A module is a React component that WordPress editors can place on a page. Keep module code small and ordinary. If you already understand React and TanStack Query, you understand this system.

## Create a module

```bash
npm run module:create -- promo-banner
```

This creates:

- `promo-banner.definition.json` — fields WordPress authors can edit.
- `promo-banner.data.ts` — API response types only. Delete it when no custom types are needed.
- `promo-banner.tsx` — server-side preparation.
- `promo-banner.view.tsx` — visible React and client hooks.
- `promo-banner.module.scss` — optional scoped styles.
- `promo-banner.props.autogenerated.ts` — generated; never edit it.

Then run:

```bash
npm run modules:generate
```

## Create an API route

```bash
npm run api:create -- promotions query
```

This command creates only the Commerce API and its Next.js route. APIs and modules are intentionally isolated, so the command works even when no module exists.

You normally edit only `app/api/commerce/promotions/Promotions.ts`. It contains five numbered values:

1. Commerce API path.
2. Upstream method: GET, POST, PUT, PATCH or DELETE.
3. Static or dynamic payload.
4. Commerce query parameters.
5. Returned data.

The Commerce base URL, API version, OUN, channel settings, Axios instance, token interceptor, refresh handling and errors are already connected.

Connect it to a module only when that module is ready:

```bash
npm run action:create -- promo-banner promotions /api/commerce/promotions client
```

## Add a GET data action

```bash
npm run action:create -- promo-banner promotions /api/commerce/promotions client
```

The result is deliberately small:

```json
"dataActions": {
  "promotions": {
    "endpoint": "/api/commerce/promotions",
    "method": "GET",
    "execution": "client"
  }
}
```

Only change `execution` to switch between `client` and `server`. WordPress does not expose this technical choice.

## GET data with React Query

Define only the response type in `<module>.data.ts`:

```ts
export interface Promotion {
  id: number;
  title: string;
}

```

Use the generic helper in `<module>.view.tsx`:

```ts
const promotions = useDataAction<Promotion[]>(
  action,
  { category: "featured", page: 1 }, // URL query parameters
  serverData,
);

promotions.data;
promotions.isLoading;
promotions.isFetching;
promotions.isError;
promotions.error;
promotions.refetch();
```

For possible server execution, `<module>.tsx` uses the matching helper:

```ts
const serverData = await loadDataAction<Promotion[]>(action, {
  category: "featured",
  page: 1,
});
```

Both helpers read the same `execution` value from the definition. There is no second server/client setting. The header is the complete working example.

## POST, update and delete

Do not add writes to `dataActions`. Payloads are dynamic, so use standard React Query mutations in the module:

```ts
const dimensions = useApiMutation<Result, DimensionInput>({
  endpoint: "/api/commerce/product-dimensions",
});

dimensions.mutate({ recordId: 123, requestedDimensions: [1, 2] });
dimensions.data;
dimensions.isPending;
dimensions.isError;
dimensions.error;
dimensions.reset();
```

Create an isolated mutation endpoint with:

```bash
npm run api:create -- add-to-cart mutation
```

## Infinite lists and pagination

Use `useInfiniteDataAction` for load-more or infinite-scroll lists:

```ts
const products = useInfiniteDataAction<ProductsResponse>({
  action,
  params: {
    categoryId,
    search: searchTerm,
    sorting: sortingParam,
    refinements: JSON.stringify(refinementPayload),
  },
  pageSize: 10,
  getItemCount: (page) => page.products.length,
  getTotalCount: (page) => page.totalCount,
});

products.data?.pages.flatMap((page) => page.products);
products.isLoading;
products.isFetching;
products.isFetchingNextPage;
products.hasNextPage;
products.fetchNextPage();
products.isError;
products.error;
```

The helper automatically sends `top` and `skip` to the Next.js API. The Products API converts those into Commerce `$top` and `$skip` parameters.

A POST may still use `useQuery` when it is a read with a fixed payload, as Microsoft Commerce sometimes requires. Put that POST in a Next.js GET route, as the categories example does. The browser performs a simple GET; the server route sends the required Commerce POST.

## Where code belongs

- `definition.json`: WordPress fields, resources and simple GET action settings.
- `data.ts`: module API and custom types only; remove it if unused.
- `tsx`: call `loadDataAction` for possible server execution.
- `view.tsx`: call `useDataAction`, use its query states, and use standard `useMutation` for writes.
- `app/api`: browser-facing Next.js endpoints.
- `lib/api/http`: shared Axios clients and authentication interceptors.
- `lib/api/commerce`: server-side Microsoft Commerce calls.
- `types/commerceTypes.g.ts`: generated Microsoft Commerce types.

## Rules that keep this easy

1. Never create an Axios instance inside a module.
2. Never put authentication or token refresh inside a module.
3. Never call the external Commerce URL from the browser.
4. Keep runtime payloads in TypeScript, not JSON.
5. Use `useDataAction` for declared GET reads and normal `useMutation` for writes.
6. Read execution only from the module definition.

## WordPress fields and composition

Config supports `string`, `text`, `number`, `boolean`, `color`, `select`, `url`, and `image`. Resources support locales such as `en`, `fr`, and `fr-ca`.

Editors can place modules beside Gutenberg blocks, create Module Fragments, create Page Templates, and select global header/footer fragments under **Settings → Headless Frontend**. WordPress automatically synchronizes deployed definitions.
